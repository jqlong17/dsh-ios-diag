## 背景 / 问题

第一批已经能导出 `events.jsonl` + `links.jsonl`（25 事件 / 29 链接那次）。
但导出来是一堆行，**没人会手写 join**。本体的价值要落到「查询」上才算闭环：

> 给一个 `id`（或未来的 `rpcId`），把它前后相连的对象和链接拉出来。

## 目标与非目标

**目标**

- `ios_events_query { runId | dir, id?, rpcId? }`：
  - 不传 id：返回这份 run 的类型统计 + 前几条事件（当目录索引）。
  - 传 id：以该事件为中心，返回与它直接相连的节点和边（一跳）。
  - 传 rpcId：返回带该 rpcId 的所有事件（网络对象进来之前，通常为空）。
- 链接要区分 `method=id`（事实）与 `method=time`（推断），响应里分开给。
- 纯函数 `selectNeighborhood(events, links, { id, rpcId })` 可单测，不碰文件系统。

**非目标**

- 不做多跳图遍历 / 最短路径（现在一跳就够回答「这条消息身边有什么」）。
- 不引入图数据库。
- 不做网络对象（等抓包权限解决）。

## 参考实现（Prior art）

- **OpenTelemetry 的 Trace 视图**：给一个 `span_id`，按 `parent/child` 展开一条链路。
  采用它的「中心 + 邻居 + 边」结构；不采用它的 span 语义（我们的对象不止 span）。
- **`jq` 的查询习惯**：用户会先看目录、再收窄。所以不传 id 时返回索引，而不是报错。

## 方案

### 第 1 步：`core/query.js`

- `loadRun(dir)`：读 `events.jsonl` / `links.jsonl`，坏行跳过。
- `selectNeighborhood(events, links, query)`：
  - `id`：找中心事件；边 = 所有 `from===id || to===id`；节点 = 中心 + 边另一端的已存在事件。
  - `rpcId`：先筛出带该 rpcId 的事件，再对每个做一跳。
  - 返回 `{center, nodes, facts, inferred}`，其中 `facts` 是 `method=id` 的边，
    `inferred` 是 `method=time` 的边——**分两个字段，不合并**。
- **为什么分字段**：报告会直接引用这个结构；合并成一个数组，调用方迟早会把推断当事实。

### 第 2 步：工具

- `ios_events_query` 加进 `TOOL_SPECS`。
- `runId` 优先；也接受绝对路径 `dir`（报告里引用目录时可以直接粘）。
- 默认只返回 50 个事件（索引模式），避免刷屏。

## 被否决的方案

| 方案 | 否决理由 | 依据 |
| --- | --- | --- |
| 上 SQLite 建表查询 | 一次 run 几十条边，加载进内存做 join 更快；SQLite 增加文件与迁移成本 | 当前数据量 |
| 多跳遍历 | 现在没有可靠的多跳链接（只有 run 与打点区间），多跳只会放大推断误差 | 第一批只有两种链接 |
| 只返回 id 列表 | 调用方还得自己回表；直接给节点 + 边更省一步 | 报告生成场景 |

## 代价与风险

- 代价：多一个模块 + 一个工具（约 150 行）。
- 风险：`rpcId` 现在几乎全空，查询会返回空——工具描述里要写明「等网络对象」。

## 未决问题

- 网络对象（`rpc_request` / `ws_frame`）何时进来（依赖抓包权限）。
- 要不要做「按时间窗筛选」（比如只看某次打点之后 10 秒）。
