## 背景 / 问题

网络对象（`RpcRequest` / `RpcResponse` / `WsFrame`）是把「消息 → 请求 → 响应」串起来的
关键一节。但抓包被 macOS 的 BPF 权限挡着（`/dev/bpf0` 只有 root 可读），
用户又不在电脑边，装 ChmodBPF 这件事只能等。

**抓包和解析可以拆开**：抓包需要权限，解析只要一个 pcap 文件。
先把解析做出来，等权限一到就能直接接上；用户自己用 Wireshark 抓的文件也能立刻用。

## 目标与非目标

**目标**

- `parseTsharkFields(text)`：纯函数，把 `tshark -T fields` 的输出解析成
  `rpc_request` / `rpc_response` / `ws_frame` 事件，以及「请求 → 响应」链接。
- `ios_net_analyze { path }`：对本地 pcap 跑 tshark，返回事件、链接、摘要。
- 用一份**合成的 pcap**（`test/fixtures/net-sample.pcap`，297 字节）做端到端验证，
  不依赖真机、不依赖抓包权限。
- 单测覆盖解析层。

**非目标**

- 不做实时抓包（等 ChmodBPF）。
- 不做 TLS 解密（抓到的 HTTPS 只有握手和长度）。
- 不把 pcap 结果自动合并进已有 run（下一步再做合并与查询）。

## 参考实现（Prior art）

- **`tshark -T fields`**：只取需要的列，输出是制表符分隔，比 `-T json` 小一个数量级。
  采用它的字段名（`http.request.method` / `http.request.uri` / `http.response.code` /
  `websocket.opcode` / `tcp.stream`），不自己解析 pcap 二进制。
- **Wireshark 的 `http.request_in`**：响应行会带上所属请求的 URI（同一 TCP 流），
  这让「请求 → 响应」的关联不需要我们猜。
- **不采用 `-T json`**：一次抓包几万帧，JSON 会到几百 MB；fields 模式足够。

## 方案

### 第 1 步：字段解析（纯函数）

一行形如：

```
1794643000.000000000|0|GET|/api/session/list|
```

- 有 method → `rpc_request`，id `req:<stream>:<序号>`
- 有 status → `rpc_response`，id `res:<stream>:<序号>`，带 `durationMs`（与同流最近请求的差）
- 有 ws opcode → `ws_frame`
- 时间转 ISO（复用事件表的 `ts` 约定）

链接：同一 TCP 流里，请求 → 最近一个响应，`method: "id"`（stream 是标识），`confidence: 0.9`。
**为什么不是 1**：同一流上可能复用到多个请求，stream 只能保证「同一条连接」。

### 第 2 步：工具

- `ios_net_analyze { path }`：校验文件存在 → 跑 tshark（关闭校验和检查，合成包没有真校验和）
  → 返回 `{counts, events, links, durationMs}`，最多返回 100 条事件。

## 被否决的方案

| 方案 | 否决理由 | 依据 |
| --- | --- | --- |
| 自己写 pcap/HTTP 解析 | 已有 tshark，自研解析器是纯负债 | 用户「优先用现成工具」 |
| 等权限装好再一起做 | 解析和抓包本就解耦；等一天不如先做解析 | 当前阻塞点只是抓包 |
| 用 `-T json` | 体积大、字段层级深 | 实测 fields 输出一行即可用 |

## 代价与风险

- 代价：多一个模块 + 一个工具（约 180 行）。
- 风险：合成的 pcap 没有真实校验和 → 解析时要关掉校验和检查；真机抓包不受影响。
