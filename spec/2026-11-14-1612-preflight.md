## 背景 / 问题

用户的真实工作场景：人在外面，电脑在家里。**真机测试是一次高成本事件**，
能不带就不带。但「这次改动能不能上真机」现在只能靠感觉。

需要一条命令，在模拟器上把「上真机前应该确认的事」过一遍，给出 pass / warn / fail 清单，
并说明每一条是怎么来的——**判断可以保守，但依据必须可查**。

## 目标与非目标

**目标**

- `ios_preflight { bundleId, udid? }`：对模拟器里的目标 App 跑 6 项检查，返回清单 + 结论。
- 纯函数 `buildChecklist(inputs)` 负责判定规则（可单测）。
- 每项检查带 `status`（pass/warn/fail/unknown）、`detail`（数字）、`how`（怎么算的）。
- 结论：任一 fail → `fail`；否则任一 warn → `warn`；否则 `pass`。

**非目标**

- 不替代真机测试；清单只回答「模拟器上能提前发现的部分」。
- 不跑 UI 交互（功能回归仍靠演示模式/手工）。
- 不做网络抓包（等权限）。

## 参考实现（Prior art）

- **Flutter / React Native 的 `doctor`**：把「环境是否满足」做成一条命令 + 结构化输出。
  采用它的形态（清单 + 状态 + 修法），不采用它的环境检查项（我们查的是 App，不是工具链）。
- **`sysdiagnose`**：官方把「该留的证据」打包。采用它的**清单化**思路，作为将来真机取证包的前身。
- **不采用**：把阈值写死在代码里不给解释——每项必须带 `how`，否则没法反驳。

## 方案

### 第 1 步：规则纯函数

输入（都由采集层提供）：

```jsonc
{
  "app": {"name":"DSH Pocket","version":"1.0.8","build":"10","debug":true},
  "running": {"pid":58620},          // 或 null
  "memoryMB": 50.3,                  // 或 null
  "logs": {"total": 120, "errors": 7},
  "crashes": [{"name":"x.ips","mtime":"..."}],
  "containerMB": 180
}
```

规则（每条都写进 `how`）：

| 项 | pass | warn | fail |
| --- | --- | --- | --- |
| 进程在跑 | 有 pid | — | 没有 pid |
| 构建类型 | Release | Debug（数字不代表真机） | — |
| 内存 | < 200 MB | 200–400 MB | > 400 MB |
| 日志错误 | ≤ 5 条/2 分钟 | 6–20 条 | > 20 条 |
| 崩溃 | 近 7 天 0 条 | ≥ 1 条 | — |
| 容器大小 | < 200 MB | ≥ 200 MB | — |

**为什么阈值这样定**：200 MB 是模拟器上「打开会话 + 图片」的常见量级；
真机 jetsam 阈值远高于此，但模拟器上超过 400 MB 已经说明视图树或缓存有问题。
数字是**经验值**，写在 `how` 里，允许被推翻。

### 第 2 步：采集层

- 设备/构建：`simctl listapps` + `plutil` 取版本号；bundle 里 `.debug.dylib` 判断 Debug。
- 内存：`footprint -j <pid>` 读一次（和采样同源）。
- 日志：已有的 `queryLogs`（最近 120 秒），按 `error|fail|timeout|refused` 计数。
- 崩溃：`~/Library/Logs/DiagnosticReports` 里匹配 App 名的 `.ips`，近 7 天。
- 容器：`simctl get_app_container … data` + `du -sk`。

### 第 3 步：工具与落盘

- `ios_preflight` 加进 `TOOL_SPECS`。
- 结果写 `docs/measurements/_runs/preflight-<时间>/report.md`，返回绝对路径 + 清单。

## 被否决的方案

| 方案 | 否决理由 | 依据 |
| --- | --- | --- |
| 直接上真机才检查 | 违背「少用真机」的初衷 | 用户场景 |
| 清单项全靠人工 | 不能回归、不能脚本化 | 现有 workflow |
| 把阈值藏进代码 | 判断不可反驳，出问题无法归因 | 规范要求「依据可查」 |

## 代价与风险

- 代价：6 项采集，跑一次约 5–10 秒（`log show` 最慢）。
- 风险：阈值是经验值，可能误报；所以每项都带 `how`，并允许 `unknown`（比如没在跑就没有内存数）。

## 未决问题

- 阈值要不要按项目配置化。
