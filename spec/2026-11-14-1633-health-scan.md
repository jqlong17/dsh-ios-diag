## 背景 / 问题

被测项目有自己的 `check-architecture.sh`（fact.json 判违规）和 `coverage-gate.sh`（xccov 判覆盖率），
但都要求在那个仓库里跑脚本、依赖它的配置。作为外部工具，我们缺一个**只读、统一、可对比**的健康视图：

- 哪些文件超过 400 行（规范阈值）？
- 哪些规则在持续违规（函数过长、强制解包、类型过大）？
- 这次和上次比是变好还是变差？

## 目标与非目标

**目标**

- `scripts/health-scan.mjs --target <repo> --project <slug>`：
  - 只读数行数（>400 行/文件）、跑 SwiftLint（装了才跑）、聚合规则；
  - 报告写到本仓库 `docs/measurements/<项目>/<时间>-health.md`；
  - `--gate` 时有超限或 Error 级违规退出码 1（可进 CI）。
- SwiftLint 用**本仓库的** `configs/swiftlint.yml`（400/150 阈值 + 6 条结构规则），
  不往目标仓库写任何文件。
- 纯函数（数行、超限、聚合、渲染）可单测。

**非目标**

- 不做自动修复。
- 不跑测试覆盖率（xccov 需要先跑带 coverage 的测试，属于被测项目的 CI 步骤）。
- 不替代被测项目自己的架构脚本。

## 参考实现

- **SwiftLint 0.65**（已装）：`file_length` / `type_body_length` / `function_body_length` /
  `cyclomatic_complexity` / `force_unwrapping` / `todo`。采用它的规则与 JSON reporter。
- **被测项目的 `check-architecture.sh`**：用 `fact.json` 判违规。我们不重复实现，
  只是把它的结论作为外部视图的一部分（将来可调用）。
- **不采用** SonarQube / CodeClimate：一套服务端，对单人项目过重。

## 方案

1. `core/health.js`：`countLines` / `findOversize` / `aggregateLint` / `renderHealthReport`。
2. `configs/swiftlint.yml`：只开结构规则，阈值对齐规范。
3. `scripts/health-scan.mjs`：走目录（跳过 node_modules/.build/DerivedData 等）→ 数行 →
   SwiftLint（可选）→ 渲染 → 写报告。
4. `--gate` 退出码约定，供将来接 CI。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 往目标仓库写 `.swiftlint.yml` | 违反只读边界 |
| 用 SonarQube | 需要服务端与账号，收益不成比例 |
| 只数行数 | 漏掉「函数太长 / 强制解包」这类真问题 |

## 测试计划

| 用例 | target | 断言 |
| --- | --- | --- |

| 坏 JSON | 同上 | 返回空 |
